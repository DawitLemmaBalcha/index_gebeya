# User Interaction Tracking (Analytics)

> **Status:** ⚠️ NOT YET FULLY IMPLEMENTED (see pending-behaviors.md for gaps)

---

## Overview

Every buyer action — views, searches, alert creations, image searches — is recorded as an interaction event. These events power the Recommendation Feed and provide behavioral data for future analytics.

---

## Behavioral Rules

### 1. Event Capture

**Rule 1.1 — Fire-and-Forget Logging**
All interaction events are logged asynchronously. The buyer's experience (search results loading, page rendering) is never delayed by analytics logging. If logging fails, the buyer is not informed.

**Rule 1.2 — Logged Interaction Types**
The following interactions are tracked:
- **search:** A text search was performed. Metadata includes the query text and result count.
- **image_search:** An image search was performed. Metadata includes the uploaded filename.
- **view_item:** A product detail page was viewed.
- **create_alert:** An alert was created. Metadata includes the query text, max price, and preferences.
- **delete_alert:** An alert was deactivated. Metadata includes the alert ID.
- **Generic events:** The frontend can also submit arbitrary event types with custom metadata via a dedicated events endpoint.

**Rule 1.3 — Event Attribution**
Each event is attributed to:
- A known user (if the buyer is authenticated via Telegram and their user ID is available).
- An anonymous session (if the buyer is not authenticated but a session identifier exists).
- Neither (in which case the event has limited utility for personalization but still contributes to trending).

**Rule 1.4 — Metadata Flexibility**
Events carry an optional metadata payload that can contain any structured information relevant to the interaction. This is stored as flexible text — not rigidly typed.

### 2. Session Management

**Rule 2.1 — Client-Generated Sessions**
Session identifiers are generated by the frontend (in the buyer's browser/Telegram Mini App) and stored locally. The backend trusts whatever session ID is provided — it does not validate or expire sessions.

**Rule 2.2 — Session Persistence**
A session ID persists until the buyer clears their browser storage or the Mini App storage is reset. There is no time-based session expiry.

**Rule 2.3 — User ID Persistence**
If a buyer's Telegram user ID becomes known (e.g., through the Mini App's initData), it is stored alongside the session ID. Future events from the same browser will include both identifiers.

### 3. Privacy & Ad-Blocker Avoidance

**Rule 3.1 — Endpoint Naming**
The analytics endpoint is intentionally named `/activity` rather than `/analytics` to reduce the likelihood of being blocked by browser ad-blockers or privacy extensions.

**Rule 3.2 — No Third-Party Sharing**
Interaction data is stored only within the system's own database. It is not sent to any external analytics service.

## Error Behaviors

| Scenario | System Response |
|----------|----------------|
| Analytics logging fails (DB error) | The error is logged to console. The buyer's action completes normally. |
| Event metadata is malformed | The event is still stored, but metadata may be null. |
| Session ID is missing from request | The event is logged without session attribution. |
| Backend is under heavy load | Logging is queued via background tasks; events may be lost if the process crashes. |
