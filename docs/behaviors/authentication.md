# User Identity & Authentication

> **Status:** ⚠️ NOT YET FULLY IMPLEMENTED (see pending-behaviors.md for gaps)

---

## Overview

The system identifies buyers through their Telegram account. Different entry points use different verification methods, but the goal is the same: reliably associate actions with the correct buyer.

---

## Behavioral Rules

### 1. Entry Points & Auth Methods

#### 1.1 Mini App (Web Frontend)
**Rule 1.1.1 — Telegram initData Verification**
When a buyer uses the Mini App (embedded in Telegram), their identity is passed via Telegram's `initData` string. For review submissions, this string is cryptographically verified using HMAC-SHA256 with the bot token as the secret key.

**Rule 1.1.2 — Auto-Registration**
If the verified Telegram ID does not match any existing user, a new user account is created automatically with the buyer's Telegram first name and username.

#### 1.2 Bot Commands (/alert, /myalerts)
**Rule 1.2.1 — Internal Service Bypass**
When the Listener (bot) communicates with the Backend on behalf of a buyer, it passes the buyer's Telegram ID as a plain integer and includes a special header identifying itself as an internal service. This bypasses the stricter Mini App verification.

**Rule 1.2.2 — No Cryptographic Check for Bot Commands**
Commands issued directly to the bot do not go through cryptographic verification because the bot already knows the buyer's Telegram ID from the Telegram API.

#### 1.3 Anonymous Browsing
**Rule 1.3.1 — Session-Based Identity**
Buyers can browse the Mini App without any Telegram authentication. In this case, they are identified only by a random session ID generated by the frontend and stored in the browser.

**Rule 1.3.2 — Restricted Actions for Anonymous Buyers**
Anonymous buyers cannot create alerts or submit reviews. These actions require Telegram identity.

### 2. Alert-Specific Authentication

**Rule 2.1 — Dual Auth Path**
The alert creation endpoint supports two authentication paths:
- **External (Mini App):** Requires the full Telegram `initData` query string containing a `user` field. Rejects plain integers and placeholders.
- **Internal (Bot Listener):** Accepts a plain integer Telegram ID, but only if the request carries the internal service header.

**Rule 2.2 — Strict Rejection for Non-Telegram**
If a request arrives from outside the Telegram ecosystem (e.g., a regular browser hitting the API directly) and tries to create an alert, it is rejected with: "Restricted: Alerts can only be managed from inside the Telegram Mini App."

**Rule 2.3 — Placeholder Rejection**
The authentication system specifically detects and rejects placeholder values like "user_id_placeholder," preventing accidental or malicious use of test credentials.

### 3. Frontend Identity Storage

**Rule 3.1 — Session ID Generation**
When the frontend first loads, if no session ID exists in local storage, a random identifier is generated and persisted. This identifier is sent with every subsequent API request as a header.

**Rule 3.2 — User ID Extraction**
If the Mini App is opened inside Telegram, the frontend can extract the buyer's Telegram user ID from the `initData` and store it for future requests.

## Error Behaviors

| Scenario | System Response |
|----------|----------------|
| Mini App initData is missing or invalid | Review/Alert creation is rejected with an authentication error |
| initData passes crypto check but user field is missing | Rejected with "Invalid User Data" |
| Bot token is not configured on the server | All authentication fails with "Server config error" |
| Internal service header is missing but a plain integer ID is sent | Rejected — treated as an external request with invalid initData |
